# Maintaining Platydoc and the XNU source handbook

Platydoc owns the source-based technical handbook in `docs-ai/`, its tools and generated book. Apple XNU is a separate, read-only input under `xnu/`, which may be a checkout or submodule. These instructions cover researching, expanding, correcting, regenerating and carrying the handbook forward to another XNU release. Keep documentation, build artifacts and maintenance instructions outside `xnu/`; documentation work must not modify that source tree.

The reader is technically capable but may be new to XNU. Explain how concrete operations work, which objects hold state, what decisions change execution, and how subsystems interact. Favor exact structures, fields, function bodies, small source excerpts and useful diagrams over terminology without explanation.

The user's requested scope controls the work. For documentation tasks, treat kernel source as evidence; do not change kernel implementation to make an explanation or check pass. Preserve unrelated user edits. Routine documentation expansion and correction are Markdown-only: do not rebuild HTML unless the user explicitly requests generation. The user will rebuild the book as needed and request inspection of that output. Continue regenerating Markdown navigation and validating links, exact excerpts, licenses and standalone SVG diagrams without running the HTML build.

## 1. Orient before editing

Start with:

- [Documentation home](docs-ai/README.md), [architecture](docs-ai/architecture.md) and [reading guide](docs-ai/reading-guide.md).
- [Complete contents](docs-ai/table-of-contents.md) and the relevant subsystem `README.md`.
- [Coverage and verification](docs-ai/coverage.md), [coverage audit](docs-ai/coverage-audit.md), [expansion history](docs-ai/expansion-audit.md) and the applicable report in `docs-ai/audits/`.
- [Source-reference index](docs-ai/source-index.md), which maps cited files back to their explanations.
- [HTML build instructions](docs-ai/development/building-html.md) when changing the rendered book or its tools.

Read existing chapters before adding another one. Keep introductory routes readable and link them to deeper companion chapters. Extend an existing explanation when that avoids duplicating the same mechanism in multiple places.

Use `rg` and `rg --files` to locate symbols, declarations, callers, configuration guards and build selection. Read surrounding implementation and cleanup code, not only search hits. Follow function pointers, operation tables, generated-interface declarations and assembly entry points when they are part of the path.

Current documentation originated from the `xnu-12377.121.6` snapshot, now stored under `xnu/`. Do not assume that folder names, old chapter counts or earlier research conclusions describe a newly supplied tree. Establish which checkout is actually being documented.

The project root contains `make_docs.py`, `AGENTS.md`, `docs-ai/` and `xnu/`. Run documentation commands from that root. Run kernel-only searches from `xnu/`, or prefix their source paths with `xnu/` when remaining at the project root. Unless explicitly project-relative, kernel paths shown in prose and source-inventory metadata (for example `osfmk/vm/vm_map.c`) are relative to `xnu/`.

Remove or deliberately retain historical pages only after checking their contents and incoming links. Otherwise stale pages remain in the book.

## 3. Research and technical depth

For each substantial mechanism, establish the following where applicable:

1. **Entry and execution context.** Who calls it, through which syscall/trap/message/callback/interrupt or internal API? Which architecture, exception level, thread context, interrupt/preemption state and configuration apply?
2. **Objects and representation.** Identify structures/classes, important fields, handles, namespaces and lookup paths. Explain how related objects point to or own one another.
3. **Normal operation.** Trace the actual dispatch and implementation decisions through to their observable result. Name the intermediate representations and state transitions.
4. **Ownership and synchronization.** Track references, locks, publication, queues, wiring, rights or page ownership. Explain which locks are dropped before calls or waits, and what must be revalidated afterward.
5. **Failure and partial progress.** Identify validation, allocation/copy faults, retry, blocking, cancellation, rollback and output publication. An error return does not necessarily mean no state changed.
6. **Exit and teardown.** Explain completion, release, close, deallocation, deferred reclamation and interrupted-operation resumption. Distinguish logical death from final storage release.
7. **Variants and boundaries.** Keep ARM64/x86, legacy/PPL/SPTM, kernel/user, client/server, 32/64-bit and feature-conditioned paths separate when their behavior differs.
8. **Evidence and limits.** Cite the code supporting the explanation and state which branches, providers, generated artifacts or external implementations were not inspected or are absent.

Use worked examples when they make representation changes understandable. For memory, distinguish CPU virtual addresses, physical addresses, object/descriptor offsets, page-table entries and IOVAs. State the selected page size, translation regime and configuration before doing address arithmetic. For IPC, distinguish a task-local port name, a right, a port object, a queued message and the receiving routine. For assembly, explain registers, stack/saved-state layout, vector or trap selection and the return instruction in the path actually shown.

For interface catalogs, retain number/ID, signature and direction, condition, capability/admission rules, implementation dispatch, data transfer, result/error behavior and implementation boundary. Do not treat a declaration, registered dispatch entry and working provider body as interchangeable evidence.

A source comment is evidence of intent, not proof of the implementation. If a comment disagrees with the body, explain the discrepancy. A same-name search hit is not proof of a caller/receiver relationship. Inspect actual call sites, registration and conversion paths.

Use local source as the primary authority for this version. If architectural or external documentation is necessary, identify it as external evidence and separate its contract from what this checkout implements. Do not reconstruct missing APFS, firmware, hardware drivers, trusted monitors, secure-kernel services, policy providers or generated stubs as if their bodies were present. Recheck those availability boundaries for each release.

## 4. Markdown, citations and source excerpts

### Chapter structure and navigation

- Give each chapter one opening `#` title, a short orientation paragraph and relative links to its parent guide and related mechanisms.
- Use `##` and `###` headings for stable, descriptive sections. The generators recognize ATX headings, not arbitrary raw HTML headings or setext underlines.
- Follow the existing technical style: explain the operation first, then its objects and decisions. Use tables for parallel mappings and code/diagrams where prose alone would be difficult to follow.
- Keep substantial new chapters reachable from the relevant subsystem index and the handbook home. Do not rely on search as their only discovery route.
- `docs-ai/tools/build_toc.py`'s `GROUPS` defines both Markdown TOC and HTML chapter order. A new page in an existing group is discovered automatically; add its stem to the preferred order when appropriate. A new directory requires an explicit group.
- Every `.md` file anywhere below `docs-ai/` is discovered as a handbook page. Do not put scratch notes, copied package READMEs or vendor Markdown there unless they are intended, classified chapters. Use temporary files outside the tree or non-Markdown formats for build-only notices.
- When renaming headings/pages, update incoming links. The checker and HTML builder preserve a shared slug convention: lowercase, remove punctuation except word characters/hyphens/spaces, replace spaces with hyphens, retain underscores, and suffix duplicate headings with `-1`, `-2`, etc. Do not assume another renderer's anchor rules.

### Source references

Use links relative to the Markdown file, with the symbol or its role in the label. Prefer `#L123` or `#L123-L140` when the reader should inspect a specific passage. These links become highlighted source-preview popups in HTML.

A chapter under `docs-ai/subsystems/<area>/` links to XNU with `../../../xnu/osfmk/...`; a chapter directly under `docs-ai/` uses `../xnu/osfmk/...`. Links to Platydoc tools, other chapters and root instructions resolve within the project instead: for example `../../../AGENTS.md` from a subsystem chapter. Compute paths rather than copying another page's depth blindly.

Keep source-inventory and implementation-location fields in authored catalog JSON/TSV relative to `SOURCE_ROOT` (for example `bsd/kern/kern_proc.c`), without adding `xnu/`. Embedded Markdown links in metadata are different: they must resolve from the generated chapter and therefore include the appropriate `../../../xnu/...` destination. Generated book source records use project-relative paths, including `xnu/` for kernel files.

Keep citations near the claims they support. Link important type definitions, field declarations, dispatcher entries, decision branches and cleanup bodies. A link to the start of a large file is usually insufficient for a detailed assertion. Avoid workstation-specific absolute paths in the handbook.

**Line bounds are not semantic validation.** The link checker can accept an old citation whose line numbers now point to unrelated code. Re-find the named symbol and read the target on release updates, even when the link remains in bounds.

### Verbatim excerpts

Interesting branches and structures should be copied inline when that helps the explanation. Each exact excerpt needs:

1. A visible source citation with file and inclusive line range.
2. An HTML comment in the exact form `<!-- source-excerpt: RELATIVE_PATH#LSTART-LEND -->`.
3. Immediately on the next line, a plain triple-backtick language fence such as ` ```c `, followed by the exact selected source lines and a plain closing triple-backtick fence.

Use real paths/numbers in the marker, not the placeholders above. The marker's path is relative to the chapter. The checker requires a range even for a one-line excerpt (`#L123-L123`).

Preserve tabs, spaces, indentation, comments, blank lines and every line in the selected range. Do not insert `...`, annotations or rewritten expressions inside a marked excerpt. Split disjoint selections into separate marked excerpts. Put explanations before/after the fence. The comparison uses `splitlines()`, so line-ending encoding itself is not the invariant.

Label pseudocode, reduced examples and hypothetical values as illustrative and keep them separate from exact excerpts. Do not remove an excerpt marker merely to suppress a mismatch; inspect the new implementation, update the explanation and recopy the intended lines.

`check_links.py` includes excerpt verification; `check_excerpts.py` can run it alone. Source-excerpt comments are not visible citations and are not a substitute for the ordinary link used by the source index and HTML source browser.

## 5. Diagrams

Author diagrams in fenced `mermaid` blocks in Markdown. Use diagrams to show ownership, address transformations, queues, dispatch, state transitions and entry/exit paths. Label arrows with the action or transferred object; distinguish calls from ownership and asynchronous completion.

Keep diagrams faithful to the surrounding explanation. An omitted error path should not look like a guarantee of success. Use separate diagrams when architecture/backend differences would otherwise be hidden. Explain any simplification.

The HTML build generates standalone SVG, preserves the Mermaid source below it and supports enlargement. Do not replace editable diagrams with screenshots or manually maintained output SVG.

The offline renderer supports the book's flow/state diagrams and sequence messages, notes and `alt`/`opt`/`loop` frames. The browserless backend rejects unsupported constructs. Literal semicolons in sequence-message labels must be escaped as `#59;` to avoid being parsed as statement separators. Quote complicated node labels and validate the rendered result.

Keep strict rendering enabled. Fix malformed input or implement/test missing renderer support; do not silently drop diagrams to obtain a successful build.

## 6. Routine documentation changes

For an explanation correction or expansion:

1. Read the current chapter, its parent/index and the relevant source.
2. Identify the operation, boundaries and evidence needed. Decide whether to extend the page or add a companion.
3. Write the explanation, citations, exact snippets and diagrams. Update related reading routes and terminology.
4. If the affected page is generated, edit its authored inputs or generator instead, then regenerate that output.
5. Regenerate navigation and run the Markdown/source checks.
6. Update current coverage/backlog records when the reviewed scope changed. Preserve historical counts as historical.
7. When the user explicitly requests HTML generation, rebuild and inspect the changed reading route, diagrams and source previews. When the user supplies an already rebuilt book, inspect that output without regenerating it.

From the Platydoc project root (the directory containing `make_docs.py`):

```sh
python3 docs-ai/tools/build_toc.py
python3 docs-ai/tools/build_source_index.py
python3 docs-ai/tools/check_links.py
```

A normal `python3 make_docs.py` already runs those three steps before HTML conversion. Do not repeat expensive checks without a new change or an unresolved concern.

## 7. Interface catalogs

### BSD system calls

`xnu/bsd/kern/syscalls.master` supplies numbers, signatures, conditions and audit/output declarations. Read the actual handler and helpers before updating `docs-ai/interfaces/bsd-syscalls/descriptions.json`. Its keys and implementation locations are checked, but its prose still requires human/agent source review.

```sh
python3 docs-ai/tools/build_bsd_syscall_catalog.py --inventory-only
# Inspect changes and update descriptions.json before the full render.
python3 docs-ai/tools/build_bsd_syscall_catalog.py
python3 docs-ai/tools/build_bsd_syscall_catalog.py --check
```

`--inventory-only` writes the inventory; it is not a read-only check. Preserve conditional alternatives, placeholders, unsupported stubs and aliases. Numbered-call enumeration does not exhaust commands inside `ioctl`, `fcntl`, `sysctl`, information/state flavors or driver/protocol namespaces.

### Mach traps

Review the source trap table, ABI/argument structures, architecture dispatch and the generator's curated purposes. Update the authored sections of `mach-traps.md` separately from its generated block.

```sh
python3 docs-ai/tools/build_mach_trap_catalog.py
python3 docs-ai/tools/build_mach_trap_catalog.py --check
```

The current extractor contains version-specific assumptions, including a 128-slot assertion and curated slot/condition handling. A new release may require a real parser/model update. Do not remove assertions or relabel old counts just to make the command succeed.

### MIG messages

The collector reads declarations only below the shared `SOURCE_ROOT` (`xnu/`); see the source-discovery contract in the next section.

```sh
python3 docs-ai/tools/build_mig_catalog.py
```

The generator uses system `cpp`, explicit `PROFILES`, and source declarations. It is not the MIG compiler, a generated wire-layout verifier, or a product kernel build. It omits type includes during preprocessing and indexes selected C/C++/Objective-C implementation files heuristically. Review `PROFILES`, `REGISTERED`, `DECLARATION_ONLY`, name normalization and receiver classification when source selection changes.

Update `descriptions.tsv` and `mechanisms-*.json` for new or changed operations. Preserve argument direction, request/reply semantics, reserved slots, capability conversion/destruction, configuration variants and missing-provider boundaries. Reconcile declarations outside the profile matrix by inspecting the guards; do not silently omit them.

For metadata-only edits against an unchanged source/profile/code inventory:

```sh
python3 docs-ai/tools/build_mig_catalog.py --render-only
```

`--render-only` trusts saved inventories and does not establish that they match the current checkout. There is currently no MIG `--check` equivalent. Inspect generated diffs and summary/inventory consistency, then run the handbook checks. Full generation can write inventories/pages before a later validation failure; inspect partial changes and preserve authored inputs while correcting the problem.

## 8. Updating to another XNU release

### Keep source discovery clean

Source discovery is rooted in `xnu/` through `docs-ai/tools/paths.py`. Documentation, generated books, caches and archived releases outside that directory are not kernel input. Keep this boundary explicit when adding scanners: source inventories and declaration/body discovery must use `SOURCE_ROOT`; documentation discovery uses `DOCS`; book links and output paths use `PROJECT_ROOT`.

Do not place another release, generated source copies or documentation output inside `xnu/`. A recursive scan confined to the selected source root can still discover files placed there. Preserve the source-only input boundary, including when initializing or updating a submodule. The presence check verifies required XNU directories and license material; it does not prove the checkout matches the release cited by the prose.

BSD implementation discovery, MIG declaration/profile collection and implementation-body indexing, and coverage inventory have different selection/filtering rules within that root. Review those rules when a release changes; a shared root does not make the tools exhaustive or equivalent.

### Release procedure

1. **Establish provenance.** Record the release identifier, source origin, available commit/archive identity and old/new tree locations. If Git history is unavailable, say so; do not invent a commit. Keep old trees outside `xnu/`, and record the selected submodule commit when one is available.
2. **Preserve the previous state.** Retain the last good Markdown/metadata and generated manifest/book through the repository's available versioning or a separate copy. Do not overwrite user edits while importing a release.
3. **Inventory changes.** Use a source diff when possible. Compare added/deleted/renamed files and declarations, not just line counts. The previous HTML `build-manifest.json` provides hashes for cited files and documentation/tool inputs; it does not inventory every kernel file.
4. **Map impact to chapters.** Use `source-index.md`, incoming citations, the catalogs and the subsystem guides. Include callers, dispatch tables, structure layouts, configuration/build files, assembly offsets and external boundary changes. Newly added uncited code still needs triage.
5. **Review changed behavior.** Re-read affected operations, predicates, lifetime/locking rules, errors and teardown. A function keeping its name does not establish unchanged semantics. A successful excerpt comparison does not validate uncopied branches.
6. **Reconcile interfaces.** Make discovery source-only, regenerate declaration inventories, update authored metadata and any parser/profile assumptions, then regenerate catalogs. Review additions, removals, renames, changed signatures/conditions and reserved slots. Remove stale generated pages only after review.
7. **Update narrative and evidence.** Re-find source locations, refresh exact snippets, revise diagrams and explanations, and adjust cross-links. Avoid blanket line-offset replacements or copying new code without reconsidering the prose.
8. **Record partial migration honestly.** If only some subsystems have been reviewed, identify the new target snapshot and list reviewed/unreviewed areas in coverage or a release-specific audit page. Do not imply all retained chapters were revalidated. A new `audits/release-<version>.md` can record changed paths, findings, unresolved boundaries and checks.
9. **Update current version labels.** Check `docs-ai/README.md`, relevant introductions, coverage records and release-specific text. The HTML builder currently hardcodes the snapshot in its footer, landing-page edition and manifest in `docs-ai/tools/book/build.py`; update all three coherently. Search for the old identifier, but preserve intentional historical references and baseline labels.
10. **Regenerate, validate and review.** Refresh navigation, run Markdown/excerpt/catalog checks, build the HTML when requested, review generated diffs and test changed browser features. Report remaining stale areas and unavailable implementation explicitly.

After the selected `xnu/` input and authored catalog metadata are ready, the integrated refresh/build command from the Platydoc root is:

```sh
python3 make_docs.py --refresh-catalogs
```

This command runs the three catalog generators and the book build. It does not research changed semantics, update the authored catalog introductions automatically, regenerate the historical audit baseline, or remove obsolete catalog pages for you.

### Coverage and audit history

Preserve `docs-ai/audits/inventory.json` and the historical scope described by `coverage-audit.md`. The current `audit_inventory.py` overwrites that baseline path and has no alternate-output option. Do not run it as a routine “refresh all” step. To create a new baseline, first provide a separate destination/workflow, verify its `SOURCE_ROOT` selection and label both snapshots unambiguously.

Use `check_links.py`'s counts and the audit helper's `explanatory()`/`source_links()` functions for current navigation/citation measurements without overwriting the baseline. Update counts from actual results, not remembered totals.

A cited file is not a fully reviewed file; physical source lines are not reviewed lines; a generated declaration is not an implementation explanation. Do not turn citation ratios into a percentage of the kernel understood.

The whole-Skywalk expansion program in the networking audit is a backlog, not completed coverage merely because Skywalk syscall entries exist. Apply that distinction to every planned expansion: record completed paths, partial work and missing providers separately.

## 9. HTML build and reader maintenance

The stable entry point is:

```sh
python3 make_docs.py
```

Default output is `docs-ai-html/index.html`; default reusable cache is `.docs-cache/`, both under the Platydoc root and outside `xnu/`. Options include `--output`, `--cache`, `--jobs`, `--refresh-catalogs` and `--check`. Use `python3 make_docs.py --help` for the current interface.

Build dependencies are Python 3.10+, Pygments from `docs-ai/tools/book/requirements.txt`, `cmark-gfm`, Node.js 20+, and Chromium or Graphviz as appropriate. MIG refresh additionally uses `cpp`; inventory tooling uses `rg`. Install missing dependencies through the available environment's normal mechanism; avoid repeated unbounded network/download attempts.

Diagram modes:

- `DOCS_DIAGRAM_RENDERER=auto`: try Chromium and fall back to the pinned Mermaid parser plus Graphviz/native SVG.
- `DOCS_DIAGRAM_RENDERER=parsed-svg`: select the browserless backend directly.
- `DOCS_DIAGRAM_RENDERER=browser`: require Chromium; `CHROMIUM_PATH` selects its executable.

For an environment where Chromium is blocked:

```sh
DOCS_DIAGRAM_RENDERER=parsed-svg python3 make_docs.py
```

The output is a self-contained local book. Preserve chapter navigation, outlines, section anchors, previous/next links, search, alphabetical concept/interface index, code formatting, source previews and SVG enlargement.

Reader data contracts are implemented jointly in `book/build.py`, `book/source_codec.py` and `book/assets/book.js`: root-relative book URLs, page-relative asset loading, source-citation attributes, shared `window.XNU_NAV`, and compressed `window.XNU_SEARCH`, `window.XNU_CONCEPT_INDEX` and lazy `window.XNU_SOURCES` payloads. See [compact static storage](docs-ai/development/building-html.md#compact-static-storage) for the schema. If changing either side, test nested chapters, the landing page, `file://` URLs and an HTTPS project path.

Preserve `file://` browsing: current search/source data use local classic scripts. A fetch-only API, module imports, CDN assets, remote fonts or a mandatory server can break that contract. Search covers the documentation and its code excerpts, not an exhaustive full-kernel text index. Source popups load referenced source files and show selected lines/context; full-file links preserve range navigation.

Each file's Pygments token data is stored once, losslessly compressed. Source wrappers retain their `_sources/<path>.html` URLs but create line/heading anchors in the browser. Full-file rendering must materialize every line for native browser Find, selection, copying and printing; do not silently replace it with a viewport-only rendering. Exact-byte Blob downloads preserve original line endings, BOMs and invalid UTF-8. Markdown inputs and license notices use the same path. Source views/downloads, search and the A–Z index require JavaScript; chapters, complete contents and SVG remain directly readable.

`source-records.json` supplies the verifier with payload locations, raw/payload hashes, line counts and heading aliases. Validate decoded contents before accepting virtual anchors. Check compressed search/index destinations too. Preserve both the native browser gzip path and the local fallback, with malformed-data and byte-preservation tests; never require a CDN or server decompression.

The book is local by default. Do not introduce hosting, publication, account requirements or analytics as part of routine documentation maintenance.

### Caches, staging and dependency upgrades

- Source tokenization is cached under `.docs-cache/source-codec/` by file content, basename, Pygments version and `CODEC_VERSION` in `book/source_codec.py`. Bump that constant if changing tokenization or record semantics. After a successful compact build, the obsolete `.docs-cache/highlight/` cache from older builds may be removed without invalidating diagram caches.
- Diagram caches hash source/label, renderer configuration, requested backend, renderer code and the vendored Mermaid manifest. Installed Chromium/Graphviz/font versions are not included. Use a fresh cache directory when validating those upgrades or a change in which backend `auto` can use.
- The Mermaid bundle is pinned by per-file hashes and provenance/license records. Preserve notices and embedded licenses. A runtime upgrade must update the manifest, entry module and transitive imports, and check the fallback adapter's dependency on internal module/export names. Do not patch minified vendor files as a substitute for fixing authored input or renderer code.
- Keep output/cache directories separate from Markdown sources and outside the read-only `xnu/` input. The builder stages and checks output before replacing the last book; `.xnu-book` marks generated output/staging/backup directories. Do not bypass protections by deleting an unmarked directory.
- Preserve Apple source notices and the generated book's license/provenance links. Do not remove source headers from copied source pages.

## 10. Validation and completion

Choose checks appropriate to the change:

| Change | Required evidence |
| --- | --- |
| Authored Markdown or source excerpts | Relevant source review, regenerated navigation if needed, `check_links.py` with zero errors. |
| BSD/Mach catalog inputs or extractor | Regenerate affected output, run its `--check`, inspect the resulting catalog and run handbook checks. |
| MIG input/profile/extractor | Source-only discovery, full collection when source changed, inspect inventories/summary/output diffs, then handbook checks. Metadata-only `--render-only` requires unchanged inventories. |
| New/changed diagram | Strict SVG rendering and inspection of the result, not merely a balanced Markdown fence. |
| HTML generator/index/source-preview logic | Python and JavaScript regression checks, successful full build and relevant browser interaction checks where available. |
| New XNU release | The release procedure above, updated scope/provenance and explicit accounting of areas not revalidated. |

Regression commands:

```sh
python3 -B -m unittest discover -s docs-ai/tools/book/tests -v
node docs-ai/tools/book/tests/assets.test.mjs
```

Existing-output validation:

```sh
python3 make_docs.py --check
```

`--check` validates the existing HTML/anchors/assets/SVG; it does not rebuild or prove freshness against current Markdown. A normal build already performs generated-output validation. `check_links.py` checks local paths, line bounds, headings, fences, reachability and exact marked excerpts; it does not verify semantic claims, resolve every C configuration, fetch external references or render diagrams.

For browser changes, inspect representative nested chapters, long interface tables, light/dark themes and narrow layouts. Exercise search for a symbol and phrase, index filtering, source-popup range/context controls, full-file line navigation and diagram enlargement using local files. The JavaScript regression tests use a small DOM fixture; they are not a browser rendering test. If browser launch is blocked, report that limit and use the available static/logic/SVG checks without claiming visual verification.

Do not build or boot the kernel merely to validate documentation. Source analysis, static documentation checks, browser checks and kernel runtime tests are different evidence and must be reported separately.

## 11. Parallel work, process limits and handoff

Use parallel agents for independent subsystem research or review when useful. Assign disjoint page/metadata ownership. All agents may share the workspace, so avoid concurrent edits to shared indexes, catalog outputs and central coverage records. Have one coordinator integrate navigation and run final generation/checks.

Each research handoff should state the inspected paths and key symbols, architecture/configuration, main decisions, ownership/error behavior, edits, checks and unresolved boundaries. Review another author's complex paths against source when the change involves subtle lifetimes, locking, assembly or security boundaries.

Use bounded subprocesses and finite polling. The tooling has timeouts for Markdown conversion, preprocessing, source workers and diagram rendering; preserve them when changing tools. Do not wait indefinitely on a browser, subprocess or agent. Inspect progress, stop only the task-owned stalled work, and continue independent work or report the concrete blocker. Keep the user informed during long operations.

Finish with a concise report of:

- Authored pages/metadata and generated artifacts changed, with useful links.
- Source scope and release/configuration covered.
- Commands/checks run and their actual results.
- Browser or runtime checks not performed and any remaining documentation gaps.

Do not claim completion from page counts alone. Completion means the requested mechanisms are explained at the agreed depth, citations/excerpts are current, navigation works, generated output is refreshed when in scope, and limitations are stated accurately.
